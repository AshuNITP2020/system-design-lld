Elevator LLD · Design note

Two Towers, One Dispatcher

Why a static singleton dispatcher is the wrong tool for this design — seven failures in plain language, every one of them reproduced from the elevator code as it stands today.

Here is the shortest demonstration. Two buildings are created in one program, each with its own elevator. A rider in the first building presses the UP button on floor 6. This is the unmodified Building class:

Program output

A rider standing in TOWER A, floor 6, presses UP.
  Tower A's elevator has 0 pending request(s)
  Tower B's elevator has 1 pending request(s)
  >>> The rider in Tower A is waiting for a lift that is moving in Tower B.

A person pressed a button, and an elevator in a different building started moving. Nothing crashed. Nothing was logged. The rider simply stands there, and no one is coming.

Where all of this comes from

The word static does not mean "shared" or "convenient". It makes a much stronger statement about the world:

There is exactly one of these in the entire program, it lives forever, and any code anywhere can reach it and replace it.

That is three separate claims, and for a dispatcher that owns a specific fleet of elevators in a specific building, here is how they hold up:

  • FalseThere is exactly one dispatcher. A company with two towers needs two.
  • FalseIt lives forever. Every test wants a fresh one, and every new building overwrites the last.
  • TrueAny code anywhere can reach it and replace it. This one is accurate, and that is exactly the problem.

Each of the seven failures below is one of those claims coming due.

1

The last building built steals everyone's buttons

Every new building calls ExternalButtonDispatcher.init(...) in its constructor. There is only one global slot to write into, so the second building overwrites the first. Last one wins.

The dangerous part: Tower A's buttons never held a reference to Tower A's dispatcher. They hold nothing at all. They ask the global slot at the moment of the press, and by then the slot says Tower B.

Instead of each building having its own control room, every building in the city dials the same phone number. Whoever answered most recently is who you get. The rider in Tower A dials, and a dispatcher in another building picks up and sends one of their lifts.

What it costs youA bug that silently produces a wrong answer is far worse than one that crashes. A crash tells you where to look. This one produces an unhappy rider and no evidence at all.
2

The test that passes alone and fails in the suite

You write a test for a two-car building. It passes. A teammate writes a test for a three-car building. Now yours fails, but only when it runs after theirs, and if the test runner uses multiple threads, only sometimes.

You will spend an afternoon re-reading your test, which is correct, and your controller, which is also correct. Neither one is the problem. Both tests write into the same invisible slot, and whichever ran last wins.

What it costs youThis is the origin of the flaky test: it passes on your laptop and fails in CI. It is the most demoralising category of bug to chase, because the fault is never in the code you are reading.
3

The phone that still rings on the old desk

After a second init(), getInstance() hands out a brand-new object. But anything that took a reference earlier still holds the old one, and the old one still works perfectly.

Reproduced from the current code

same instance after re-init?  false
request landed on fleet-1 car? true   (fleet-2 car received 0)

The building hires a new dispatcher and gives them a new desk and a new phone. The old desk is cleared out, but the old phone is still plugged in, and a few buttons are still wired to it. Press one of those and your call rings on an empty desk in a closed office.

What it costs youHalf the system can be talking to the current dispatcher and half to the retired one. Both appear to work. Neither is correct, and nothing in the compiler can tell you which half you are in.
4

The constructor that lies to you

Six months from now, someone reads this line and believes it:

new ExternalButton(5, Direction.UP)

Two arguments, both obviously necessary, nothing missing. So they build a lobby kiosk, or a diagnostic tool, or a test fixture that creates a button directly — and it fails at run time.

It is like a form that asks for your name and address. You fill it in completely, and the clerk rejects you because you did not bring a document the form never mentioned. The requirement was real. It was just invisible.

The IllegalStateException message in the code is genuinely good; it tells the person exactly what to do. But it is still a message delivered while the program is running, possibly in production, rather than a red underline in the editor before anyone commits.

5

Anyone can re-wire the building, from anywhere

init() is public and static, so any line of code in the entire program can call it and silently change where every button in the building sends its calls. No ownership, no permission, no warning.

It is a switch in a public hallway that re-wires the whole building, and the only label on it reads "init". Nothing stops a cleanup refactor, a debug utility, or a well-meaning new teammate from flipping it.

6

Two threads that see two different answers

This one surprises most people, so it is worth the background.

A modern processor does not have one single memory that every thread reads from. Each core keeps its own fast local copy of recently used values. When one thread writes to a shared variable, threads on other cores may keep reading their stale local copy for a while — unless the language is explicitly told to push the update through to everybody.

The static field here is not marked volatile, so Java makes no promise about when other threads see what init() wrote. In practice: the building starts, a background thread handles an early button press, and it sees null, throwing "init must be called before use" even though init() definitely already ran.

Someone updates the notice board in the lobby while everyone else is reading photocopies they took that morning. There is no rule saying when they have to walk back and check the board.

What it costs youThis fails roughly once in a thousand startups, never on your laptop, and only on the production machine with more cores.

A final field set in a constructor comes with a real guarantee from the language: once the object is handed out, its final fields are fully visible to everyone. Injection gives you that fix for free.

7

The shopping list that is not a copy

Building passes its own live ArrayList into the dispatcher, and the dispatcher stores that exact object rather than a copy. Two classes now own one list.

You give someone your shopping list, except it is not a photocopy — it is the same sheet of paper. You cross something off later, their list changes too, and neither of you realises.

Today nothing modifies the list after construction, so it works by luck rather than design. The day someone implements "take a car out of service" by removing it from the building's list, the dispatcher's fleet silently changes underneath it. If that removal happens on another thread while a strategy is looping over the fleet, you get a ConcurrentModificationException thrown from inside code that looks completely innocent.

What constructor injection replaces all seven with

This button uses this dispatcher. It was decided when the button was built. It can never change.

No global slot for a second building to overwrite. No stale handles, because nothing is handed out on request. No hidden requirement, because the dependency is in the constructor signature. No way for distant code to re-point it, because there is nothing to re-point. And a final field carries a genuine thread-visibility guarantee.

In the elevator code this is two extra parameters, threaded through the composition root that already exists:

// Building — already the composition root
ExternalButtonDispatcher external =
        new ExternalButtonDispatcher(List.copyOf(controllers));
for (int f = 0; f < numberOfFloors; f++)
    floors.add(new Floor(f, external));

// ExternalButton
private final ExternalButtonDispatcher dispatcher;   // set once, never reassigned

public void press() {
    dispatcher.dispatch(floorNumber, direction);
}

The List.copyOf closes problem seven in the same stroke, and init and getInstance can both be deleted.

So when is a singleton actually fine?

The pattern is not evil. It is a strong claim that happens to be false most of the time. One question settles it:

Could a reasonable person ever want two of these at the same time?

For a logger facade or a stateless maths utility the answer is no. One is genuinely all that can exist, and it holds no state anybody could corrupt. For a dispatcher that owns a specific fleet of elevators in a specific building, the answer is obviously yes — and the Tower A / Tower B output at the top of this page is what "yes" looks like when the code insists otherwise.

Every failure on this page was reproduced against the elevator design as it currently stands, not reasoned about in the abstract.
